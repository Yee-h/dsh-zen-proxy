# Design

## Context

现状与本次实测到的事实（全部带来源与日期；未复核的一律标注为未复核）：

- **宿主契约（已查证，权威）**。`@deepseek-ai/dsh-llm` 的 `normalizeModelInfo` 在 `reasoning !== undefined` 时要求 `reasoning.efforts` 为非空数组、且 `reasoning.defaultEffort` 必须落在该数组内，否则抛 `INVALID_MODEL_REASONING`；`resolveCallWithInfo` 在 `reasoning === undefined` 而调用方指定了档位时抛 `UNSUPPORTED_REASONING_EFFORT`，在档位不在 `efforts` 内时同样抛 `UNSUPPORTED_REASONING_EFFORT`；`prepareCall` 通过 `adapterDefaults.reasoningEffort` 标记「档位由适配器自己声明」。`listModels` 的条目只保留 `{provider, id, name, description?, inputModalities?}` 五个字段（多余的键被静默丢弃、不报错），因此 `reasoning` 不在该路径声明。
- **本车道的事实（参考实现实测，2026-09-24）**。网关接受 `reasoning_effort`、`thinking.budget_tokens`、`enable_thinking`、`thinking_budget` 后**忽略**它们——每种拼写 3 次采样，`low` 产生的思考 token 比 `xhigh` 更多；这些未知字段偶尔以 503 露出。唯一被执行的旋钮是输出预算：64 token 的上限把思考从约 397 token 压到约 63。（本机已在两个可用模型上独立复现，见 `evidence.md` (1)。）
- **本次取值（`https://models.dev/api.json`，取值日期 2026-10-07，2026-10-08 复核）**。opencode provider 下本车道的 11 个免费模型全部 `reasoning: true`（逐行见 `evidence.md` (2) 的 `reasoning` 列；受检 11 条、非 `true` 者 0 条）；其 `limit.context` 与 `limit.output` 与本仓库溯源表**逐行相同**（受检 11 条、不符 0 条）。`jev-1.13-free` 在该 provider 中不存在。**注意**：`reasoning: true` 只说明这些模型公布思考能力，**不**等于「无法关闭思考」——后者是参考实现的私有标记 `canDisableThinking`，models.dev 不提供，本机无溯源来源（见 `evidence.md` (2b)）。
- **本仓库自己的复核实测已完成**，见本变更的 `evidence.md` (1)：同一 prompt、同一组身份头、唯一变量为请求体字段。结论是**复现了参考实现的观测**——`high` 的思考量低于 `low`、基线为五者最大、同设置两次重复的离散与跨设置之差同量级（字段被接受但未被执行）；而输出预算被精确执行。

## Goals / Non-Goals

**Goals**

- 让模型选择器的思考强度入口出现，且选中的档位**真的改变线上行为**。
- 档位说明里的数字与将要发出的数字由同一个计算得出，不出现「界面写 8K、线上发 16K」。
- 档位计算不编造任何无溯源的数值。

**Non-Goals**

- 不尝试用 `reasoning_effort` 等字段表达强度：该车道忽略它们（见 Context 第 2 条）。
- 不为「是否能关闭思考」引入逐模型的能力标记：该属性无可溯源来源，见 D18。
- 不新增配置项，不改变两条路由、可用性判定、身份伪装与协议族分派。

## Decisions

### D15 思考强度的唯一载体是输出预算

档位不映射到 `reasoning_effort` 之类的字段，而是映射到请求体的输出上限（chat 族 `max_tokens`、responses 族 `max_output_tokens`）。依据是 Context 第 2 条：该车道接受但不执行 effort 字段，且接受未知字段有 503 风险；而输出预算被实测执行。

**这条决策的可证伪条件已判定为「不成立」**：若 `reasoning_effort` 确实改变思考量，本决策不成立。本机复核（`evidence.md` (1)）给出了相反结果——`high` 的思考量（均值 404）低于 `low`（均值 770），基线 877 是五者最大，且同设置重复的离散（136 / 227）与跨设置之差（366）同量级，`n=2` 下无法据此判定存在效应；唯一被精确执行的是输出预算（`max_tokens=512` 时两个模型的合计都恰为 512 且 `finish=length`）。**D15 成立，不直传任何 effort 字段。**

### D16 三档 = 三段预算，档位名后紧跟被执行的数字

`light` / `balanced` / `deep` 三档的名义天花板是 2048 / 8192 / 模型容量，实际发出的预算按 D18 的 2 倍系数放大为 4096 / 16384 / 模型容量——档位名称里显示的是**在调用方未指定上限时将要发出的那个数**（菜单在声明期生成，此时还不知道调用方的上限；调用方一旦给出更小的上限，实际发出的值会被收窄，见 `zen-free-upstream-wire` 的「调用方上限收窄档位预算」）。档位**不用**形容词（"low"/"high"）表达，因为在这条车道上强度只有预算这一个维度；预算数字直接写进档位**名称**（`精简 · 4 K`），而不是只放在描述里：宿主把 `name` 渲染成菜单项，用户在选择前就能看到该档将发出多大的上限；描述只解释「上限同时约束思考与正文」。名称里的数字与决定请求的同一个 `budgetFor` 调用生成，避免界面数字与线上数字分叉。

### D17 容量项取 models.dev 的 `limit.output`

容量项（`deep` 档的上限，以及各档的封顶）取自 models.dev 的 `limit.output`，与既有的 `limit.context` 用同一个来源 URL、同一个取值日期、同样逐条记录模型 id 的溯源纪律（见 `src/catalog.js`）。无溯源的 id（当前仅 `jev-1.13-free`）回退到 32768 并在 evidence.md 记为已知限制，**不**用家族猜测填充。

### D18 阶梯各档按 2 倍给出：思考与正文共享同一个天花板

`max_tokens` 同时限制思考与正文，因此一个「留给正文一半」的阶梯比「把同一数字既当预算又当答复长度」更接近用户的预期。倍率 2 的标定边界是**思考占比 ≤ 50%**（正文 = 2 × 基准 × (1 − 占比) ≥ 基准 ⟺ 占比 ≤ 50%），本机复核的 33%-43% 落在边界内。本车道的 11 个模型按 models.dev 全部为 `reasoning: true`（有溯源，见 `evidence.md` (2)），故该 2 倍统一应用，而**不**引入 `canDisableThinking` 之类的逐模型标记——那类属性本机没有任何可溯源来源，编造它正是既有需求明令禁止的。代价是：对「本可关闭思考」的模型该系数偏大（本机无法识别哪些模型属于此类，见 `evidence.md` (2b)）。

### D19 预算恒为不小于下界的正整数

档位计算对每个输入先做「有效数字」判定：调用方给出的非正数、`NaN`、`Infinity` 一律视为**没有**该上限，而不是当作 0。否则设置页清空输入框产生的 `0` 会把每一轮都压到最小预算。计算结果再以 `MIN_BUDGET` 取下界，保证正文总能落地。

### D20 用请求体预算，不用 `defaultMaxTokens`

宿主的 `defaultMaxTokens` 物化出的上限**与档位无关**，无法表达三档。因此本变更把档位折算成预算直接写进请求体（与参考实现一致），并**继续不声明** `defaultMaxTokens`——「能力元数据」需求中关于 `defaultMaxTokens` 的省略纪律因此仍然成立，需要改的只是同一段末尾那句与输出预算互斥的话。

## Risks / Trade-offs

- **答复变短**。此前单轮上限是模型容量，此后是档位预算。默认档 `balanced` 在倍增后为 16384，仍低于本车道最小可溯源输出上限（32000），因此默认行为不会因容量不足而失败；但长答复可能以 `length` 结束，用户可用 `deep` 换回全量。
- **`jev-1.13-free` 的容量项无溯源**。回退值 32768 可能高于该模型真实上限（未复核）。该 id 实测长期处于瞬时不可用组，通常不进目录；一旦进入目录而回退值过高，表现是上游拒绝该请求，而不是静默错误。
- **2 倍系数的标定边界**。倍数的用意是让档位名里的数字成为正文的**下界**，这要求思考占比不超过 50%。本机实测在 `mimo-v2.6-flash-free` 上思考占比为 33%-43%（`nemotron` 的推理计数器自相矛盾、不可信，见 `evidence.md` (1) 的口径），`light` 档仍能达标；参考实现曾在该模型上测得约 82%，两者不一致，说明**占比随预算与请求而变**——本机在 512 token 上限下观察到思考吃掉 100% 的预算（正文 0 字符），即预算越小、思考占比越高。对思考占比长期高于 50% 的模型，档位名里的数字就不再是正文的下界；本机未做多预算点采样，无法给出该阈值的具体位置。
- **实测覆盖面**。本次复核只在两个可用模型上取证（受免费车道配额与可用性限制），其余模型按同一阶梯统一处理；未逐一实测的模型记为未复核。
